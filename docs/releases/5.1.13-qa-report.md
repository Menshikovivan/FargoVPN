# FargoVPN 5.1.13 — QA report

## Acceptance result

- Full pytest: **123 passed, 1 skipped**.
- Focused release browser regression: **7 passed**.
- Rendered panel pages: **17/17**.
- Browser panel audit: **29 total buttons / 28 executable pass / 0 fail; 11 selects / 8 executable pass / 0 fail; 17 checkboxes / 15 executable pass / 0 fail; 0 console errors**.
- Python/JS/shell syntax checks: PASS.

## What was reproduced on 5.1.12

The focused Chromium regression reproduces the message redirect when the page-specific controller is unavailable: the generic POST fallback follows the server redirect and navigates to the user card. The same harness then loads the 5.1.13 controller and verifies no navigation, event echo, cleared input, and preserved focus.

The same pattern was reproduced for the logs filter and GitHub authorization: without the page controller no AJAX action runs; with the 5.1.13 page controller the action executes in place.

The publish test verifies that the 5.1.12 generic panel controller cannot start the GitHub upload by itself, while the 5.1.13 publish controller creates the XHR upload without navigation and exposes progress state.

## Root cause from the supplied server evidence

The 5.1.12 server was serving `panel.js?v=5.1.12`, so this was not merely an old browser cache. The deployed Nginx managed FargoVPN location in the supplied diagnostic dump did **not** contain `proxy_hide_header Content-Security-Policy` or a compatible inline-script policy, while the same server contained a strict `script-src 'self'` CSP. The application therefore had its page-specific inline controllers blocked by the effective CSP; the remaining global POST fallback followed the 303 redirect.

5.1.13 changes the installer so an update explicitly runs `nginx_panel_guard.py --once`, validates `nginx -t`, and refuses to report success unless the active nginx dump contains the required FargoVPN CSP contract. It also adds client/server version detection and Service Worker refresh handling.

## Environment limitation

The sandbox can run real Chromium through Playwright (`/usr/bin/chromium`) and therefore the release acceptance tests execute in a real browser engine. Direct `page.goto(http://localhost/...)` is blocked by the sandbox browser policy, so the focused release tests use the exact rendered application HTML/JavaScript with mocked network responses. Production PostgreSQL, 3x-ui and GitHub write APIs were not touched.

The repository's `tests/qa/run_qa.sh` also starts the same checks, but its combined execution was not stable in this sandbox (the browser audit and pytest steps themselves pass independently); the final release result therefore relies on the separately captured browser audit and full pytest logs above.

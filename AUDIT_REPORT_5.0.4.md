# FargoVPN 5.0.4 — бэкапы и проверка на пользовательских данных

Дата: 2026-10-08. Основа нового релиза — полный пакет **5.0.3**, с сохранением его исправлений. В предоставленном серверном бэкапе установлена **5.0.2**. Проверенные исходные `webapp.py`, `static/panel.js`, `static/monitoring.js`, `backup.py` совпадают с ранее выданной 5.0.2; это подтверждено побайтовым сравнением, не только VERSION.

## Что исправлено

Первопричина лишнего разбиения: `backup.py` 5.0.3, функция `split_for_telegram`, возвращала исходный файл только для размера <=1 байт, затем всегда ограничивала размер части половиной архива. Поэтому даже небольшой полноценный tar.gz уходил как part001/part002.

В 5.0.4 `backup.py:338` задаёт **45 000 000 байт** (десятичные МБ), а `backup.py:343` возвращает исходный файл до этого размера включительно. Выше порога сохранён старый алгоритм: две части при достаточном лимите или больше частей для очень больших архивов/меньшего настроенного лимита. Настройка размера части действует на большие архивы; маленькие до 45 МБ больше не дробятся даже при меньшем настроенном размере части.

Архив не переименовывается в .part и не пересжимается при отправке одним файлом. Telegram send_document получает исходный `.tar.gz`. Формат бэкапа, набор данных, отправка только в Telegram, существующие настройки и восстановление ранее разделённых бэкапов сохранены.

Ваш соединённый бэкап: **1 356 809 байт**. Проверено на нём: split возвращает ровно исходный tar.gz, каталог частей не создаётся.

## Как использован бэкап

Две загруженные части соединены в правильном порядке; результат повторно сверён с конкатенацией исходных байтов. Tar прочитан: 253 элемента, нет absolute paths, path traversal, symlink или специальных файлов. Исходные части не изменялись.

Извлечены только необходимые данные в отдельную защищённую папку (0700; SQL/SQLite/ключи/HTML — 0600). Боевой `config.py` не исполнялся; нужные VAPID-параметры читались через AST literal values. SQL-функции и код установщика из бэкапа не запускались. Не было установки/восстановления на production, действий GitHub, Telegram, платежей и изменений внешнего nginx.

Plain SQL COPY преобразован в отдельную SQLite read-модель для тестов. Это **не реальное восстановление PostgreSQL** и не проверка его блокировок/триггеров. Для данных 3x-ui родная `xui.db` открывалась read-only. Использованы production-функции нормализации 3x-ui и объединения пользователей; источник API заменён офлайн-данными бэкапа, живые online/CPU/скорость не выдумывались.

Повторный проход на бэкапе заново создавал fixture из SQL и вновь исполнял шесть страниц/240 комбинаций. Результаты совпали. Первое тестовое условие «число объединённых строк не меньше всех DB rows» оказалось неверным для local-only/отрицательных идентификаторов; проверка заменена содержательным условием сохранности **всех положительных Telegram ID**. Production-алгоритм объединения не изменён ради теста.

Изначальное извлечение COPY через простой regex некорректно учитывало пустые таблицы: новый построчный reader явно обрабатывает `\.` и не перескакивает к следующей таблице. Отдельный синтетический тест проверяет пустую таблицу, NULL, tab/newline/backslash и boolean. Неподдерживаемая декларация или нарушенный COPY вызывает ошибку, а не молчаливый успех.

## Что обнаружено в реальном Push-журнале

Есть **три исторических HTTP403 `BadJwtToken`**. Текущая сохранённая EC P-256 private/public пара совпадает; создание JWT и проверка подписи с сохранённым ключом **локально успешны**, subject с fallback WEB_DOMAIN валиден. У двух из трёх сохранённых подписок VAPID public key соответствует конфигу, у одной метаданные ключа пустые. Ключи и подписки в вашем исходном бэкапе сохранены без изменения.

Это не доказывает причины исторических отказов провайдера и не означает, что реальная доставка исправлена: нужен живой запрос и ответ Push-провайдера с часовыми/браузерными данными. Удалять все подписки или генерировать новые ключи ради предположения не стали. Имеющиеся в 5.0.3 диагностика статуса/журнал/проверка ключей и корректная обработка старых подписок сохранены. На сервере выполните Проверить → Включить → Тест в каждом использованном браузере/PWA и посмотрите свежий delivery event.

Первый тест подписи без WEB_DOMAIN ошибочно показал отсутствующий subject: причиной была неполная тестовая конфигурация. После чтения реального fallback параметра проверка прошла. Это исправление harness, не заявленный баг production.

## Обновление

Сделайте штатный бэкап. В панели 5.0.2 или 5.0.3: **Обновления → ручная загрузка и установка**, выбрать `VPN_Service_Platform_5_0_4_FULL.tar.gz`, подтвердить. Данные и настройки остаются на сервере, новый архив содержит только проект.

Консоль после размещения нового архива и SHA256 в /root:

```bash
cd /root
sha256sum -c VPN_Service_Platform_5_0_4_FULL.tar.gz.sha256
tar -xzf VPN_Service_Platform_5_0_4_FULL.tar.gz
bash FargoVPN-5.0.4/install.sh --update-existing /root/vpn_bot
cd /root/vpn_bot
cat VERSION app/VERSION static/VERSION
bash scripts/healthcheck.sh
.venv/bin/python scripts/verify_server.py --public-url 'https://YOUR_DOMAIN/YOUR_PANEL_PREFIX/'
```

После обновления создайте бэкап через панель. Если он <=45 000 000 байт, ожидается **один документ с окончанием .tar.gz**, не два `.part` файла. Проверьте его `tar -tzf`, что tar читается, и наличие дампа базы. Старые двухчастные архивы соединяются `cat backup.tar.gz.part001 backup.tar.gz.part002 > backup.tar.gz`; восстановление на копии сервера, а не поверх production ради проверки.

Ограничения: PostgreSQL сервер/реальные миграции и restore, Telegram/Push delivery, root installer/systemd restart, реальные оплаты, mobile/PWA CSS hit-testing и live 3x-ui writes/подключения не проверены. Исполнены локальная read-модель, production-функции и DOM, без боевых сетевых действий.

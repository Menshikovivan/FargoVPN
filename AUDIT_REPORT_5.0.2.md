Дата: 08.10.2026. Исходник: доступный в этой беседе архив `VPN_Service_Platform_5.0.1_FULL.tar.gz`. Архив распакован без переноса владельцев; изменялась отдельная копия. Продуктивный сервер, учётные данные Telegram/3x-ui/GitHub и его PostgreSQL не предоставлены.

**Результат:** исправлены подтверждённые кодовые ошибки; подготовлен полный пакет 5.0.2. Это не подтверждение успешной работы всех внешних интеграций на вашем сервере. Ни реальные деньги, ни сообщения клиентам, ни публикация в ваш GitHub в ходе аудита не отправлялись.

## Четыре заявленные проблемы: причины и границы подтверждения

### 1. Пользователи

В 5.0.1 сервер предварительно фильтровал массив пользователей по URL: `webapp.py:2392`. После открытия/перезагрузки отфильтрованного URL в HTML оставалась только часть пользователей. Клиентский обработчик мог работать лишь с этим неполным набором и не мог вернуть остальных при выборе «Все» или очистке поиска. В воспроизведении использованы 110 записей: 5.0.1 после сброса сохранял неполный набор, 5.0.2 возвращает 110.

Теперь исходный набор сохраняется целиком: `webapp.py:2394`. Обработчики `change` сразу применяют фильтр/сортировку, поиск использует debounce; страница сбрасывается на первую при изменении условий. Даты `registered_from/registered_to` учитываются клиентом и сохраняются в URL. Найдены и исправлены пропуск настоящего username в поисковых данных и округление дробных дней перед сортировкой: `webapp.py:2448`, `webapp.py:2463`. Безлимитная квота сортируется как Infinity.

Проверены 240 сочетаний: 5 статусов × 6 сортировок × 2 направления × 4 поисковых сценария, а также переходы страниц, последняя страница и сброс пагинации после поиска. Это проверка DOM/JavaScript, без перезагрузки и без «Применить». Физический мобильный браузер не проверен. Полная неработоспособность каждого select на чистой странице 5.0.1 не воспроизведена; подтверждён сценарий неполного набора после URL-фильтра.

### 2. Мониторинг 3x-ui

В 5.0.1 был только график CPU хоста FargoVPN; отдельных графиков CPU/скорости 3x-ui не было. Первая CPU-точка создавалась как одноточечная SVG polyline: `static/monitoring.js:32` — такая линия не видна. Стиль stroke **уже присутствовал** в исходном CSS; его отсутствие не является причиной. Chart.js не используется, поэтому исправление не зависит от CDN, Chart.js или CORS браузера к 3x-ui.

Добавлены CPU 3x-ui и график скоростей ↓/↑; первая точка образует видимую горизонтальную линию: `static/monitoring.js:24`. Данные получает серверный адаптер через `/api/xui-telemetry`; браузер не получает пароль/токен 3x-ui. Опрос — 10 секунд, серверный кэш обычно 30 секунд; скрытая страница не запускает новые опросы, `pagehide` останавливает таймер и прерывает активные запросы, возврат через BFCache возобновляет работу: `static/monitoring.js:93`.

Старая интеграция требовала исключительно Bearer: `services/xui_api.py:183`; варианты URL не включали legacy `/server/status`. Добавлены cookie-вход `/login`, CSRF до/после входа, переиспользование сессии, fallback после явного отказа Bearer при наличии сохранённых логина/пароля: `services/xui_api.py:598`. Поддержаны `/panel/api/server/status`, `/api/server/status`, `/server/status`, webBasePath, старые online/lastOnline под inbounds и чтение старых клиентов из inbounds: `services/xui_api.py:531`, `services/xui_api.py:574`.

Пустой `obj` не превращается в выдуманные нулевые метрики: `services/xui_api.py:1077`. Ошибка выводится в `mon-xui-error`. netIO и netTraffic нормализуются существующим адаптером; есть проверки счётчиков, скоростей и некорректных чисел. Сетевые ошибки POST после отправки не повторяются, чтобы не продублировать изменение подписки.

Сверка исходников: актуальный опубликованный release upstream на дату проверки — **3x-ui v3.9.0**, опубликован 03.10.2026. Прочитаны upstream `internal/web/controller/index.go`, документация API и исходники server controller. Cookie и Bearer поддерживаются текущим API; для cookie требуется CSRF. Совместимость чтения со старой схемой проверена имитацией API. Полная совместимость операций создания/изменения клиентов со всеми историческими версиями 3x-ui не заявляется: существующий write API проекта ориентирован на современный clients API.

Источники: https://github.com/MHSanaei/3x-ui/releases/tag/v3.9.0 ; https://github.com/MHSanaei/3x-ui/blob/main/internal/web/controller/index.go ; https://github.com/MHSanaei/3x-ui/blob/main/internal/web/controller/server.go ; https://docs.sanaei.dev/docs/reference/api/server/ .

### 3. Push / Service Worker

В 5.0.1 `boot()` был объявлен, но не вызван: `webapp.py:4896`. Из-за этого начальное состояние оставалось «Не проверено», журналы — «Загрузка…». Это подтверждённая причина отсутствия начальной инициализации. Обработчики кнопок в исходнике присутствовали; тотальная невозможность нажатия всех кнопок, overlay или browser-specific сбой подписки без вашего браузера не подтверждены.

Теперь boot вызывается после готовности DOM: `webapp.py:4894`. Проверка читает поддержку/HTTPS/permission, регистрацию SW, подписку браузера, VAPID и наличие именно этой подписки у текущего логина на сервере: `webapp.py:4875`, `push_service.py:318`. Сервер возвращает SHA-256 отпечатки endpoint, а не секретные URL подписок других устройств.

Кнопки проходят цепочку: enable → разрешение/SW/subscribe → сохранение; test → реальная функция отправки в фоновой задаче; disable → удаление у текущего логина и browser unsubscribe. Фактическая доставка теста определяется журналом, постановка в очередь не выдаётся за доставку. В DOM с имитацией browser API проверена вся цепочка; RFC8291/VAPID шифрование/подпись проверяются существующими независимыми криптографическими тестами. Отправка через FCM/Mozilla/APNs здесь не проверена.

Запросы журналов имеют тайм-аут и понятную ошибку, накопленный серверный журнал сохраняется при добавлении браузерных строк. Публичный адрес SW отображается полностью, добавлена ссылка. Ключ валидируется как base64url/P-256; stale SW/subscription/key mismatch обрабатываются существующим механизмом восстановления. Предварительная подготовка SW уменьшает потерю пользовательского жеста; фоновая подготовка не может перезаписать контекст после нового действия благодаря счётчику поколения. CSP разрешает диагностические запросы FCM/Mozilla. SW отдается с Service-Worker-Allowed на публичный префикс; версия меняется вместе с VERSION. Недоступный необязательный статический файл больше не срывает весь install SW, offline-fetch возвращает Response 503.

«Error retrieving push subscription» может зависеть от сети и браузера; исправление всех внешних причин этой ошибки не заявляется. Safari/iOS, PWA на домашнем экране, разрешения и настоящая доставка требуют проверки на устройствах.

### 4. GitHub / main / версия

В 5.0.1 уже был GitHub Git Data API, а не shell git; отсутствие git add, user.name/user.email не является найденной причиной. Подтверждён тихий кодовый путь: при `GITHUB_MAIN_SYNC_ENABLED=False` функция возвращала `synced=False` без ошибки, затем API/UI сообщали об успешном Release: `update_manager.py:1474`. API не возвращал SHA коммита, UI быстро уходил на другую страницу. Значение настройки и права токена именно на вашем сервере недоступны.

Теперь main sync обязателен, отключение возвращает ошибку; сохранение GitHub-настроек включает его и допускает только main. Коммит имеет сообщение `Release X.Y.Z`: `update_manager.py:1519`. PATCH ref выполняется с force=False, гонка ветки проверяется до PATCH, ответ должен подтвердить SHA: `update_manager.py:1539`. Интерфейс показывает SHA и ссылку, не скрывая результат немедленной перезагрузкой. Если Release/asset уже загружены, а main не подтверждён, это явно сообщается: `update_manager.py:1655`.

Ограничение публикации/настроек логином menshikovivan сохранено на сервере; тестируются роль сессии и настроенный логин, а не только скрытие HTML. Обычные панели остаются клиентами проверки/установки. Токен скрыт в UI, исключён из публичного main вместе с приватными конфигурациями/ключами/БД. Настройки GitHub проверяют доступ к репозиторию; окончательное доказательство записи — публикация и полученный SHA, не read-only проверка токена.

Версия читается runtime из корневого VERSION через update_manager.current_version. app/VERSION и static/VERSION — совместимые копии для старых упаковщиков, все равны 5.0.2. Панель, SW и административная сводка бота используют runtime-версию: `main.py:1907`. Сохранены проверки установщика VERSION на диске/в health/SW и передача настоящего кода ошибки. Установка обновления и публикация Release остаются разными явными действиями.

## Бот, БД и резервные копии

Проинвентаризированы 38 мест создания callback и 10 обработчиков: menu, connect, faq, show_instruction, admin, approve_, decline_, crmv_, crmmod_, crmdel_. Полный перечень функций/строк — AUDIT_INVENTORY_5.0.2.json. Существующие тесты регистрации по четырёхзначному коду, подтверждения пригласившего, защищённого доступа, оплаты, сообщений, рассылок, identities и post-success регрессий сохранены и проходят. Реальный проход каждой Telegram-кнопки требует работающего бота.

Создание клиентов без XTLS flow осталось в add_client_sync и services/subscriptions.py; update не переписывает flow существующих клиентов. FargoVPN не меняет параметры transport/портов upstream nginx, Hysteria2 или xHTTP. Однако реальный Hy2/xHTTP handshake и созданные учётные данные нужно проверить на ваших inbound. Современный API сам определяет протокольную модель; полного теста всех протоколов/версий здесь нет.

Распределение выполняется по XUI_MANAGED_INBOUND_IDS и доступным inbound, а не по захардкоженным названиям стран. Германия/Польша/Канада в коде не заданы. Без вашей карты node/inbound нельзя подтвердить, что выбраны именно эти три локации. Не добавлялась фиктивная география. Проверить selected ids и remarks в настройках, затем реальную подписку тестового клиента.

Ошибка восстановленного пользователя «диалог не начат» не обходится: Telegram запрещает боту начать личный диалог. Пользователь должен выполнить /start и пройти предусмотренную привязку/регистрацию. В панели есть понятное сообщение этой ошибки; delivery не выдаётся за success. Проверить отдельно chat not found и blocked.

Бэкап остается tar.gz, Telegram-only delivery, один canonical backup service/timer. Две части применяются к обычному архиву; если размер больше 2 × лимит части, безопасно создаётся больше частей. Каждая часть — бинарный фрагмент исходного gzip, самостоятельно не распаковывается. Соединение проверено побайтно. Восстановление папки частей в консольном установщике сохранено; реальные users-only/full, safety-backup и PostgreSQL swap/rollback требуют клона сервера.

241 статический SQL/DDL-фрагмент прошёл PostgreSQL parser после адаптера; это **не** выполнение миграций/запросов на настоящем PostgreSQL. Подготовить PostgreSQL здесь не удалось из-за ограничения владельцев/UID среды. SQL-параметры остаются связанными; динамические идентификаторы в restore нормализуются. Известные async вызовы БД/HTTP в боте уходят в threadpool; startup migration панели теперь тоже вынесена из event loop. Отсутствие всех возможных гонок и SQL-инъекций не является доказанным результатом этого аудита.

## Интеграция с внешним nginx

Прочитаны README.md и install.sh репозитория Itman75/Nginx-L4-Stream-Router-Mask-for-3x-ui. Его install.sh: строки 490–519 — настраиваемые panel/sub ports и secret paths; 2231 — upstream panel; 2433–2468 — location панели и подписок. Обычно panel 10443, subscriptions 55443, xHTTP 50443; это defaults, не обязательные реальные значения. TCP 443 принадлежит L4 router, UDP 443 может использовать Hy2. HTTPS L7 использует собственные внутренние listeners/сокеты.

Наш install.sh не пишет nginx-конфиг и не запускает guard. На обновлении действующий FargoVPN location сохраняется. На новой установке без location его должен добавить владелец внешнего nginx: scripts/print_nginx_location.py **только печатает** отдельный блок, ничего не применяя. Не заменяйте nginx.conf и stream routing этим блоком. Если полное восстановление меняет публичный префикс панели, согласовать location нужно отдельно; автоматического перенастраивания больше нет.

Итог установщика — адреса/порты/службы/логин, а подробные ошибки направлены в файл. Старый service_failure_details больше не печатает хвост системных/приложенческих логов. Полный реальный вывод установки root/systemd в этой среде не проверен.

Источник: https://github.com/Itman75/Nginx-L4-Stream-Router-Mask-for-3x-ui .

## Проверка на сервере и ограничения

Перед установкой иметь актуальный бэкап и подтвердить способ восстановления. Проверку full restore проводить на клоне, а не на единственном боевом экземпляре.

```bash
cd /root/vpn_bot
cat VERSION app/VERSION static/VERSION
bash scripts/healthcheck.sh
.venv/bin/python scripts/verify_server.py --public-url 'https://menshikovivan.site/YOUR_FARGOVPN_PREFIX/'
.venv/bin/python service_audit.py --json
systemctl list-timers --all 'vpn-service-*'
systemctl is-enabled vpn-service-nginx-guard.service
nginx -t
```

Ожидается VERSION=5.0.2; health=OK; verify_server не содержит ok=false; guard disabled/not-found. service_audit показывает одну canonical backup службу, без дублей/cron. PUBLIC PREFIX взять из установленного config.py, не подставлять старый URL автоматически.

```bash
# Проверить сохранённые несекретные настройки и входящие локации:
.venv/bin/python - <<'CHECK'
import config
from services.xui_api import inbound_selection_status_sync
print('REMINDER_DAYS:', config.REMINDER_DAYS)
print('XUI_MANAGED_INBOUND_IDS:', config.XUI_MANAGED_INBOUND_IDS)
print(inbound_selection_status_sync(force=True))
CHECK

# Сборка двух Telegram-частей перед восстановлением (имя своего архива):

tar -tzf /PATH/backup.tar.gz >/dev/null
```

Если частей больше, соединить ВСЕ в числовом порядке. Установщик может сам обработать папку частей — сохранённый пункт восстановления. После изменения reminder_days через кнопку 3x-ui проверить значение приведённой командой и повторным открытием вкладки.

Для GitHub: вход menshikovivan → настройки токена → публикация тестируемого релиза → сверить показанный SHA с https://github.com/Menshikovivan/FargoVPN/commits/main/ . При protected branch/fine-grained PAT без Contents write UI должен показать конкретную ошибку. verify_server проверяет только чтение main, не доказывает write. Публикация может успеть создать Release до отказа main; интерфейс теперь сообщает это явно.

Для Push: настольные Chrome/Firefox и мобильный Chrome Android; для iPhone/iPad — установленное PWA. Проверить permission, scope, VAPID и сохранение конкретной подписки, получить настоящее тестовое уведомление, затем выключить и проверить отсутствие подписки. DevTools Network: SW 200, JavaScript, Service-Worker-Allowed с правильным префиксом; Console без ошибок. Опрос мониторинга должен прекратиться после закрытия страницы. Одной серверной командой невозможно подтвердить browser permission/APNs/FCM и визуальную мобильную вёрстку.

Не подтверждены: реальные транзакции PostgreSQL/миграции/swap, реальные платежи/OCR внешних чеков, доставка Telegram/Push, фактический push в ваш GitHub, работа ваших стран/node, Hy2/xHTTP подключения, реальные systemd/nginx/root installation и визуальная работа на физических мобильных устройствах. Секреты в уже существующих исторических журналах новый фильтр не удаляет.

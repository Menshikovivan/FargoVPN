# FargoVPN 4.9.3 — изменения и проверка

## Причины и исправления

1. Обработчик чека создавал строку `payments` без проверки текущей заявки. Существующая защита `approve_payment_sync` предотвращала повторное подтверждение только одной строки, поэтому два разных чека создавали два независимо подтверждаемых платежа. Теперь открытие покупки выдаёт `purchase_token`, все чеки этой покупки используют один токен. Приём выполняется в транзакции с `pg_advisory_xact_lock` на Telegram ID: сначала ищется тот же токен либо незакрытая заявка (`pending`/`processing`), и только при отсутствии создаётся платёж. Повторный чек не запускает OCR, уведомления администратора или начисление. Уникальный индекс сохраняет защиту токена в БД даже после автоодобрения. Новая покупка после закрытия предыдущей разрешена через явное открытие покупки. Существующая атомарная защита подтверждения платежа сохранена.
2. Новая запись регистрации имеет `expiry_time=0`, `enable=1` и пустые данные VPN-клиента. Ранее это считалось бессрочным доступом. Наличие подписки теперь требует данных VPN-клиента (`uuid`, `email` либо `sub_id`), активность дополнительно учитывает включение и срок. Настоящие бессрочные клиенты продолжают работать.
3. Без активного доступа «Моя подписка» сообщает о необходимости оплаты и показывает кнопку покупки. В основном меню покупка расположена первой, отдельной строкой; для действующего доступа сохранено продление.
4. Список пользователей получает локальную дату регистрации при объединении с 3x-ui. Включительный диапазон дат применяется совместно с поиском, статусом и сортировкой перед пагинацией по 50 записей. Изменение фильтра возвращает первую страницу; URL сохраняет параметры. Удалено прежнее отсечение списка на 2000 пользователях. Даты вычисляются в часовом поясе панели (`WEB_TIMEZONE`); записи без известной даты исключаются только при заданных границах.
5. История переписки формировала URL медиа без существующего HTTP-обработчика и без публичного префикса в JSON. Добавлен авторизованный endpoint, выдающий медиа из существующего файлового кэша; проверяется принадлежность события пользователю. Входящие и исходящие события используют один механизм. Для исходящих фото Telegram-бота теперь сохраняются метаданные файлов. Управляемый Nginx location не устанавливал `client_max_body_size`: при стандартном лимите Nginx фото больше 1 МБ не доходили до приложения. Лимит теперь учитывает настройки загрузок и multipart overhead. Фото преобразуются в JPEG, сжимаются до лимита Telegram 10 МБ и ограничиваются по геометрии; TIFF/BMP/GIF/WebP больше не отправляются напрямую как неподдерживаемый файл sendPhoto. GIF отправляется как статичное фото первого кадра. Неподдерживаемая геометрия возвращает понятную ошибку.
6. Публикация GitHub выполняется `update_manager.publish_archive` через `github_notes`. Regex резервного чтения ожидал заголовок вида `## 4.9.2`, тогда как реальный заголовок содержал описание после версии; при несовпадении возвращалась вся история. Новый общий парсер допускает описание, дату и квадратные скобки и выбирает только текущий раздел. При отсутствии нужной версии история не подставляется. Полный CHANGELOG сохраняет старые записи; описание релиза содержит только изменения 4.9.3 и служебные метаданные архива.

## Миграция и установка

Штатный установщик вызывает `init_db.py`, который автоматически добавляет nullable-колонку `payments.purchase_token`, уникальный частичный индекс токена и индекс `(tg_id,status)`. Миграция повторяемая, не удаляет и не переписывает старые платежи; данные 3x-ui не меняются. Эквивалентный SQL находится в `migrations/payment_submission_4_9_3.sql`.

Для обновления используйте штатную установку полного архива. Управляемый Nginx location обновляется штатным установщиком/guard. Для собственного reverse proxy проверьте лимит тела запроса; приложение само ограничивает размер вложения по настройкам. Памятное состояние FSM после перезапуска не сохраняется: покупку, открытую до обновления, нужно открыть заново кнопкой меню. Существующие незакрытые заявки будут найдены в БД и повторно созданы не будут. Исторические дубли заявок, созданные старым кодом, не удаляются автоматически — их нужно сверить по реальному переводу до подтверждения.

## Автоматическая проверка

- До изменений: 86 тестов прошли.
- После изменений: 98 тестов прошли (`python -m pytest tests -q`).
- Проверены синтаксис Python, `bash -n install.sh` и JavaScript (`node --check static/panel.js`); новый JS фильтров исполняется в Node с моделью DOM.
- Зависимости установлены из `requirements-dev.txt`, включая закреплённые версии основного runtime. Для нового JS-теста дополнительно нужен Node.js.
- Конкурентный тест отправляет 20 разных чеков одной покупки из восьми потоков и получает одну строку; также проверяет повторный токен после подтверждения, незакрытую заявку и независимых пользователей. БД и advisory lock в этом тесте заменены SQLite/потоковой моделью. Живой PostgreSQL в окружении отсутствует, поэтому многопроцессную блокировку и SQL-миграцию нужно дополнительно проверить на тестовом PostgreSQL.
- HTTP-тест проходит реальный FastAPI multipart-парсинг, проверяет отправку JPEG, историю и media endpoint для обоих направлений, публичный префикс, 401 без входа и 404 чужого/отсутствующего события. Вызовы Telegram и загрузка файлов подменены; реальная доставка в Telegram не выполнялась.
- JS-тест проверяет границы дат, поиск, статус, переходы страниц, сброс страницы и отсутствие даты.
- Живой Nginx, Telegram, 3x-ui и GitHub не использовались. Опубликованная страница GitHub не менялась: подготовлена логика штатной публикации нового релиза 4.9.3.
